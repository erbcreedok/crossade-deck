# Дизайн: транзакция, поза покоя, facing, предсказание

Спроектировано, не построено (этап 3.5). Спецификация поведения — `docs/scenarios/pose.md` и
`docs/scenarios/hand-accept.md`; каждый пункт «Тогда» оттуда обязан стать тестом.

## Транзакция — спина всех authored-изменений

Переворот, дроп, реордер, поворот-при-переносе — не разрозненные осколки, а одно: **транзакция** —
авторское дискретное изменение истины нода→нода, которое едет по проводу, просит разрешения и умеет
висеть pending. Это НЕ «перемещение по холсту»: таскание и кручение под пальцем — `Transform` (ниже).
Транзакция — смена РОДИТЕЛЯ и всё, что зона решает на входе.

```ts
Transaction { actor, payload, from, to }  →      // резолвит ПУЧОК выходов, не владеет ими
   verdict     "allow" | "ask" | "deny"          // AcceptRule
   pose        { slot, position, angle, tilt, side }   // поза покоя, per-грань derive/stamp/keep
   settle      как дойти до позы во времени       // snap | hold+ease — раскладка зоны
   survival    "land" | "consume"                 // «сжигание» — карта поглощается, а не ложится
   visibility  временный грант                    // «подглядывание» — с дедлайном
```

`Move` — транзакция, где в pose-дельте есть `slot`. `Flip` — где непуста только грань `side`.
`Rotate-commit` — только `angle`. **Не разные структуры**: разница в том, какие грани непусты.
Отдельных сущностей Rotate/Move/Flip нет.

Это НЕ реестр «механик» (тот похоронен): `survival`/`visibility` — закрытый малый набор выходов
конверта, а грани позы — данные-правила зоны, не каталог трюков.

**Транзакция не узел и не наследник**: у неё нет ни места, ни картинки — она НАД узлами.

## Transform vs поза покоя — сустав «в-полёте / в-покое»

Ориентация и место карты живут на ДВУХ разных осях, и путать их нельзя:

- **Transform (в полёте)** — позиция, угол, наклон, масштаб, пока ими владеет ЖЕСТ. Локально,
  покадрово, предсказано, по проводу НЕ едет. Единственная по-настоящему локальная часть.
- **Поза покоя** — резолвнутый выход транзакции. По каждой грани зона делает одно из трёх:

| | что делает | хранит / едет? | пример |
|---|---|---|---|
| **DERIVE** | берёт из раскладки | нет, пересчёт из слота | угол в веере, позиция в сетке |
| **STAMP** | навязывает фикс, перебивая входящее | фикс | сброс: `side`=вниз; автовыпрямление: `angle`=0 |
| **KEEP** | берёт входящее и хранит | **да, едет по проводу** | свободный стол: 15° остаётся |

Карту повернули на 15° и перенесли на стол-KEEP → 15° лежит в состоянии, едет, поздний зритель и
сервер после реконнекта видят его. Автовыпрямление в 0° сразу → STAMP.

«Полежать 15° пять секунд, потом медленно в 0°» → поза покоя ВСЁ РАВНО 0°, различие в **оседании**
(`settle`): как поза-в-полёте расслабляется в позу-покоя во времени. Раскладка владеет `settle()`
рядом с `place()`; snap = мгновенно, hold+ease = с задержкой. Одни часы на всё (шов «рантайм = часы»).

**Кто решает / кто анимирует**: **def** — право и смысл; **рантайм холста** — триггеры и ЕДИНЫЕ часы
(тайминг, easing, idle-гейт); **визуал** (запись registry) — как выглядит фаза (контракт
`{phase(t), commit()}`). Новый элемент не заводит свой тикер.

## Facing — одна грань позы (`side`), ДВА реестра

`side` — дискретная грань той же позы (переворот вокруг горизонтали), угол — непрерывная. Одна семья,
не две. Правило стороны расщепляется на две оси, и ОБЕ — реестры, не union:

```ts
facing: {
  own:    RegistryRef,   // как ложится сторона на входе: derive/stamp/keep + кастом
  others: RegistryRef,   // как чужие относятся к стороне владельца
}
```

- Поставляемые `own`: **`up`**/**`down`** — STAMP · **`keep`** — KEEP. Игра регистрирует свою запись,
  читающую СОСТОЯНИЕ (цепочку контейнеров `ctx.chain`, конфиг стола), но НЕ траекторию: «открытый
  стол» перебивает `down` у стопки, вскрытие в покере на фазу перебивает `keep` у руки — и всё это
  воспроизводимо у позднего зрителя, потому что состояние общее.
- Поставляемые `others`: **`same`** (стол, борд, открытая рука) · **`back`** (строгая игра, всегда
  рубашка) · **`opposite`** (Ханаби, лицом наружу). Запись — чистая функция
  `(сторона владельца, зритель, ctx) → сторона`.

**Продавливания через `from` больше нет.** «Карта со стола сохраняет сторону в стопке» пишется НЕ
через след, а через состояние: стол при укладке ставит на карту факт (`el.faceFixed = el.side`),
стопка читает факт. Разница решающая — факт едет в состоянии и одинаков у всех, траектория живёт
только у того, кто видел перенос, и разъезжается у позднего зрителя.

**Два бита, и они не смешиваются:** `сторона у владельца = card.side XOR zone.flipped`. Ручной
переворот ОДНОЙ карты двигает `card.side`, переворот ВСЕЙ зоны двигает `zone.flipped`. «Странная»
карта остаётся странной навсегда: перевернули руку целиком — сдвинулись все, порядок сохранён. Не
запрограммировано, а следует из раздельности битов. Механика САМА СЕБЯ обозначает: владелец видит
рубашку среди лиц, стол — лицо среди рубашек, отдельного маркера не нужно.

Следствия:
- **`handOpen` — не механизм, а значение**: `others` между `back` и `same`.
- **Зона без владельца обязана иметь `others: "same"`** — остальным не относительно кого смотреть
  (валидатор спеки). Это же закрывает вопрос «откуда владелец без мест за столом» без `Seated`.
- **Владелец записан на ЗОНЕ**, из места не выводится.
- **`Private` ортогонален** — он про «карты нет в чужой картине вовсе», а не про сторону.
- **Настройка игрока, меняющая `own`/`others`, — правило игры, а не доступность**: она едет в
  состояние и авторитетна на весь стол, иначе двое видят разную правду. Четырёхцветность локальна
  ровно потому, что меняет ЛИЦО, а не сторону.

**Скрытость лица и приватность — РАЗНОЕ, и источники у них разные**: `reverse: back` прячет лицо, но
предмет на столе виден всем; `Private` убирает предмет из чужой картины ВОВСЕ.

**Четыре вида обратной стороны** (`Flippable.reverse`): `back` (скрыто ЛИЦО, все видят рубашку —
карты) · `same` (одинакова — фишки) · `mirror` (зеркало — шахматы) · `alt` (другое видимое —
шашка→дамка, двухцветная фигура). Нет поля — flip недоступен (мяч, стол).

## Предсказание: только обратимое

Клиент предсказывает то, что не стыдно отменить, и не предсказывает остального:

| | Оптимистично | Почему |
|---|---|---|
| **позиция/угол (derive-грани)** | да, сразу | обратима: карта улетит домой, и это читается как ответ |
| **поза keep-граней** | локально до эха, затем состояние | free-стол хранит позу покарточно — осознанное исключение из «едет только containment» |
| **facing (`side`)** | нет, по эху | необратим красиво: мигнуть лицом и спрятать читается как глюк |

Карта кладётся туда, куда указал палец, и лежит там со старой стороной; приехало подтверждение —
перевернулась. Полёт покрывает круг, паузы не видно. **Правило одно на ВСЕ перевороты**, включая
ручной тап — исключений нет, иначе первый же рассинхрон будет искать причину именно там. Отказ
сервера поэтому не создаёт визуального противоречия ни в одном случае: карта улетает домой, ни разу
не показав лица.

**Ожидание сервера не индицируется.** Три точки зарезервированы за ожиданием решения ЧЕЛОВЕКА
(согласие владельца руки). Ждём железку — молчим: она ответит быстрее, чем заметит глаз, либо карта
останется неперевёрнутой, что само по себе и есть сообщение.

**Политика песочницы: скрытость — правило ПОКАЗА, а не защита.** Все карты лежат на всех клиентах,
нечестный клиент увидит чужую руку через девтулзы — это принято осознанно. На этом стоит механика
запоминания: клиент ЗНАЕТ карту, игрок её не видит. Отсюда два требования: `facing` — авторитетное
состояние (иначе двое увидят разные стороны одной карты, и «где дама крестей» перестанет быть общим
фактом), а перемешивание — НАСТОЯЩАЯ анимация, а не подмена картинки (игрок следит глазами;
телепортация убивает игру). Строгим стендалонам понадобится пер-клиентская фильтрация схемы — её
закладывать отдельно и заранее.
