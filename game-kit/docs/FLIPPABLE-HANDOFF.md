## Context

Текущий `Flippable { back: string }` (`src/core/atoms/flippable.ts`) — игрушка: одно поле-поверхность и
`shownSurface(node, faceUp)`, который движком НЕ вызывается (рендер красит сырой `Surfaced.surface`,
`scenePlan.ts:225`). На серии кейсов владельца модель разваливается: переворот — это ГЕОМЕТРИЯ
(отражение в позе, дети наследуют через `compose`), у грани может быть целое ДРУГОЕ поддерево, а
«какая сторона сейчас» для стопки/колоды — это ПАРИТЕТ по цепи владельцев. Требование владельца
(дословно): хранить в атоме ссылки / гибкий конфиг, определяющий, чем узел СТАНЕТ после флипа и
обратно; у карты / контейнера / коня / стопки / колоды — свой механизм, который ещё может меняться;
без `if`-по-типу и без раздувания ядра.

Решение: атом держит только ДАННЫЕ (имя рецепта + счётчик переворотов). Поведение — в РЕЕСТРЕ
(как `render/surfaces.ts`): у каждого узла свой рецепт `turn/back`, подменяемый. Единственная правка
ядра — один шаг обхода `transformsOf` читает «показанный» узел и композит отражение. Веток по типу нет.

Согласовано с владельцем:
- **facing = `turns` (паритет, addsUp).** Единственный стейт; геометрия (det<0) — следствие.
- **Флип едет вниз двумя каналами вместе:** паритет («покажи другую сторону» — каждый узел СВОИМ
  рецептом) + отражение (геометрия, наследуется через `compose`). Стол-2/3: карта рубашкой→лицом,
  конь смотрит в другую сторону, ряд встаёт в обратном экранном порядке — всё автоматом.
- **Реордер колоды и контент стола-1 (железо+пицца)** — НЕ автоматом: это СВОЙ рецепт узла поверх
  двух каналов (что вернёт `turn(n)`).
- **Ряд/grid: оба варианта, решает рецепт.** По умолчанию геометрическое зеркало (дёшево, держит
  Case D); ряд с читаемым содержимым регистрирует рецепт с direction-flip (перераскладка RTL, но
  теряет ручные сдвиги Case D — осознанный размен, выбирается узлом).

## Дизайн

### 1. Атом — только данные (`src/core/atoms/flippable.ts`)
```ts
export interface FlippableFields {
  /** имя рецепта переворота в реестре flips. "" ≡ "mirror". */
  readonly flip: string;
  /** сколько переворотов от авторского состояния. СУММА по цепи — стопка переворачивает детей. */
  readonly turns: number;
  /** линия отражения в градусах — ПАРАМЕТР инстанса, а не пресет-на-угол. 90=Y (умолчание), 76,
      69, что угодно. Рецепты-зеркала читают его; контент-рецепты игнорят. Убивает «Axis76». */
  readonly axis: number;
}
export const Flippable = defineAtom<FlippableFields>({
  name: "Flippable",
  requires: [],                       // грань не обязательна: контейнер/стол тоже переворачивается
  defaults: { flip: "", turns: 0, axis: 90 },
  classes: { flip: "own", turns: "addsUp", axis: "own" },
});
```
`shownSurface` и поле `back` удаляются. Спека функций не держит (`assertSerializable` стережёт) —
`turn/back` живут в реестре, спека ссылается ИМЕНЕМ.

### 2. Реестр рецептов (`src/render/flips.ts`, новый — зеркало surfaces.ts)
```ts
export interface Flip {
  /** отражает ли рецепт геометрию. true → движок композит reflect(node.axis); false → чистая
      подстановка/раскладка. УГОЛ живёт в поле axis атома, не тут (потому и нет пресета-на-угол). */
  readonly reflects: boolean;
  readonly turn: (n: Node) => Node;   // чем узел становится на обороте (СВОЙ механизм узла)
  readonly back: (n: Node) => Node;   // обратное; для чистого зеркала = turn
}
registerFlip(name, flip); flipRecord(name): Flip | undefined; // dangling имя → пропуск, не throw

// умолчание — чистое зеркало: только геометрия, ничего не хранит (угол = node.axis)
registerFlip("mirror", { reflects: true, turn: (n) => n, back: (n) => n });
// библиотека переиспользуемых МЕХАНИК (полка Presets/Flips) — drop-in рецепты:
//  turnOver      reflects:true   turn: показать back-запись Surfaced          (карта: перевернулась + зеркало)
//  deckReorder   reflects:true   turn: реордер детей + их обороты             (колода целиком)
//  deckChildren  reflects:true   turn: перевернуть ТОЛЬКО детей, без реордера  (альт-режим client2)
//  contentSwap   reflects:false  turn: вернуть другое поддерево               (стол-1: железо+radial+пицца)
//  directionFlip reflects:false  turn: тот же узел с обратным direction        (ряд: читаемый RTL)
```

### 3. Примитив отражения (`src/core/transform.ts`)
```ts
/** Отражение относительно прямой под углом deg через начало. det = -1, самоинверсно. */
export function reflect(deg = 90): Transform { return chain([rotate(deg), scale(-1, 1), rotate(-deg)]); }
```
`pose()` не трогаем (остаётся det>0). Отражение композится ОТДЕЛЬНО, по паритету, как `resolveZ`
читает сумму на apply-time. Канон Transformable («в спеке нет reflection») цел.

### 4. Ядро-рендер: движок прогоняет список эффектов и про флип не знает

Если код флипа положить прямо в обход `transformsOf`, то любая следующая механика поведения узла
полезет туда же, добавляя свои строки и `if`. Обход разбухнет. Этого делать нельзя.

Вместо этого у движка есть СПИСОК маленьких функций-эффектов. Перед тем как нарисовать узел, движок
проходит по списку и у каждой функции спрашивает одно: «ты подменяешь этот узел или сдвигаешь его?».
Каждая механика кладёт в список ОДНУ свою функцию, в своём файле. Код, который проходит по списку,
пишется один раз и больше не трогается — ядро не знает, какие механики существуют.

```ts
// src/render/effects.ts
export type Effect = (n: Node, ctx: ResolveContext) => { node: Node; pre: Transform };
export function registerEffect(e: Effect): void { … }         // механика кладёт свою функцию сюда
export function applyEffects(n: Node, ctx: ResolveContext) {   // список пуст → узел как есть
  let node = n, pre = IDENTITY;
  for (const e of effects) { const r = e(node, ctx); node = r.node; pre = compose(pre, r.pre); }
  return { node, pre };
}
```
В `transformsOf`/`scenePlan` меняется ОДНА строка: вместо сырого узла берём `applyEffects(n, ctx)` —
детей/поверхность считаем по `node`, а `pre` домножаем в позу (внутри рамки узла, чтобы дети
зеркалились относительно его оси). Новая механика = новый файл с `registerEffect`, обход не трогаем.
(Если однажды понадобится эффект другого рода — не «подмени/сдвинь», а, скажем, сквозная прозрачность —
в результат добавится одно необязательное поле; это разовая правка, а не строка на каждую механику.)

**Флип — одна такая функция, в `render/flips.ts`.** Она отвечает за две вещи, и обе берёт из `turns`,
но читает их по-разному — из-за этого кейс A получается сам собой:
- **отражение** включается, когда нечётен СВОЙ `turns` узла (тот, что реально перевернули); дети зеркалятся сами.
- **подмену контента** `turn(n)` делаем, когда нечётна СУММА `turns` по цепи, и всегда рецептом самого узла.
```ts
registerEffect((n, ctx) => {
  const own = fieldsOf<FlippableFields>(n, "Flippable");
  if (!own) return { node: n, pre: IDENTITY };
  const rec = flipRecord(own.flip || "mirror"); if (!rec) return { node: n, pre: IDENTITY };
  const summedOdd = sumAlongChain(ctx, "Flippable", "turns") % 2 !== 0;
  const ownOdd = own.turns % 2 !== 0;
  return { node: summedOdd ? rec.turn(n) : n, pre: ownOdd && rec.reflects ? reflect(own.axis) : IDENTITY };
});
```
`facing(id) = sign(det(nodes.get(id)))` — хелпер инспектора/тестов; какая сторона сейчас — решает паритет.

### 5. Действие (`src/core/actions.ts`)
Обработчик `flip` = `compose(node, Flippable({ ...fields, turns: fields.turns + 1 }))`. Флип-назад — +1 по модулю 2.

## Как ложатся кейсы (A–E)
- **A (стопка):** стол/стопка own turns=1; ребёнок own 0 → суммарно 1 (нечёт) → показывает рубашку своим рецептом. Индивидуальный ре-флип: ребёнок own 1 → сумма 2 (чёт) → снова лицом; и два reflect (стол + карта) взаимно гасятся → карта не зеркалена, лицом вверх. Падает из механизма сам.
- **B (подсветка):** ОТДЕЛЬНЫЙ атом, ортогонален флипу (см. вопрос ниже) — из него растёт рефактор `surface`.
- **C-1 (стол→железо+пицца):** рецепт `contentSwap` (reflects:false), `turn` возвращает другое поддерево.
- **C-2 / C-3 (зеркало Y / 76°):** стол own turns=1, рецепт `mirror` (reflects:true), угол из поля `axis` атома (90 / 76). Карта рубашкой→лицом (суммарный паритет), конь зеркалится, ряд — обратный порядок; всё через два канала.
- **D (двинул→перевернул):** зеркало берёт узел как есть → зеркалит последний живой стейт, ничего не хранит (кроме рядов, выбравших direction-flip рецепт — их размен).
- **E (лениво):** рисуется только показанная сторона; зеркало — одна матрица, карта тривиальна, стол-со-своим-задом — свой рецепт. Стоимость различает РЕЦЕПТ, не ветка.

## Заметка на будущее: анимация ложится на этот механизм (ВНЕ текущего объёма)

Анимаций в проекте нет (были в client1/client2, в client2 выглядели прилично). Этот дизайн их НЕ
блокирует и под них уже скроен — фиксирую, чтобы продолжающий не искал разговор. Атом под анимацию
НЕ растёт: рецепт = чем узел СТАНОВИТСЯ (статическая правда, t=1); анимация = как показать переход.

Почему ложится (уже в коде):
- `Quad.transform` ЖИВОЙ, по объекту (scenePlan): «анимация, что вертит карту, не грузит геометрию».
- Transformable: «поворот, в котором ты на полпути, — анимация, а не то, что нода хранит» → атом хранит РЕЗУЛЬТАТ (`turns`, рецепт), «полпути» — дело рендера.
- `actions.ts` уже держит `flip/drag/hover/focus` как capability-gated записи без обработчиков — точки подключения событий.
- `ResolveContext.viewer` (onlooker-relative, не едет по проводу) — канал для транзиентных жестов.

Два рода событий, два канала:
- **Коммитящие (drop-flip):** меняют `turns`; анимация = поворот вокруг `recipe.axis` 0°→180°, на 90° узел ребром (det через 0 — вид настоящего переворота), там свап на `shown`-узел. Ось = та же `recipe.axis` (90/76). «7deg/90deg» — диапазон угла от события. У карты/колоды/стола/коня свой рецепт → своя ось и свой свап даром.
- **Транзиентные (hover-peek 7°, drag-lift):** НЕ трогают `turns`; живут на `viewer`-канале (показался/вернулся, коммита нет). Ховер-подгляд ≈ Tiltable-ответ на viewer-канале.

Чего нет (будущий эпик):
- слой-аниматор: tween между двумя чистыми `scenePlan` по времени + easing (модель client2);
- биндинг событие→жест (drop → turns+1 + пуск; hover → транзиент на viewer-канале);
- интерполяция ОТРАЖЕНИЯ: матрицу с det<0 не лерпить — раскладывать в `axis+angle` и гнать угол через 90°; `recipe.axis` даёт разложение бесплатно.
- (возможно) рецепт со временем отдаёт предпочтительную ось/длительность на событие — данные в реестре, не новый механизм.

## Handoff — диалог по Flippable (чтобы не переизобретать)

**Что перепробовали и ОТВЕРГЛИ — не возвращаться:**
- `Flippable { back: string }` + `shownSurface` — атом инертен, движок его не звал; флип ≠ своп одной поверхности.
- `runtime.card.faceUp` side-map по id узла — анти-паттерн `id==="deck"`; faceUp — общий стейт, не viewer.
- `down` как boolean-паритет / `flip:number %2` — флип не булев паритет одной поверхности.
- `Surfaced { back }` / `TwoSided.back: Surface` — у грани стола целое ПОДДЕРЕВО, не ссылка на поверхность.
- слот vs рекурсивный-узел vs 3-ярусный if-dispatch — отвергнуто как if-дерево и расширение ядра.
- вкладывание флип-специфики в `transformsOf` — раздувает обход на каждую механику.

**Что РЕШЕНО (подтверждено владельцем):**
- facing = `turns` (паритет, addsUp); геометрия (det<0) — следствие.
- флип едет двумя каналами: паритет (покажи другую сторону — СВОИМ рецептом) + отражение (геометрия, наследуется через compose).
- отражение ⟺ свой `turns` нечёт; контент-`turn` ⟺ суммарный паритет нечёт → кейс A выходит сам собой.
- `axis` — поле атома (не пресет-на-угол); рецепт объявляет `reflects: boolean`.
- поведение — рецепты в реестре (`turn/back`); спека — только данные (`flip/turns/axis`).
- рендер прогоняет СПИСОК эффектов (`applyEffects`); флип — одна функция; ядро не знает, какие механики есть.
- ряд: и зеркало, и direction-flip — выбирает рецепт узла.
- 6 рецептов (mirror/turnOver/deckReorder/deckChildren/contentSwap/directionFlip) собирают все юзкейсы Atoms.

**Жёсткие правила владельца (на весь эпик):**
- НЕ называть узлы голыми английскими словами-типами (`table` и т.п.) — говорящие доменные id.
- НЕ городить if-деревья по типу; масштаб — данными/реестром.
- НЕ раздувать несколько механизмов ядра ради одной фичи.
- Чинить, а не удалять; не добавлять лишнего и не сужать задачу.
- Каждый закон — с падающим СНАЧАЛА сторожем; `tsc` + весь тест зелёные; push — только с разрешения.
