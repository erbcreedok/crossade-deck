# client2 — управление, конфликты, сеть (CONTROL-DESIGN)

Статус: ВИДЕНИЕ (не реализовано). Зафиксировано, чтобы рулить будущими фичами/фиксами и не
закраситься в угол. Стол client2 пока локальный, сервера нет — но layering держим уже сейчас.
Родня: `REFACTOR.md` (E-план), `ENGINE-UPGRADE.md` (BoardFactory), `GRID-DESIGN.md` (борды),
memory `project_engine_kit_target` (kit = публичная либа) и `project_state_vs_fx_split`.

## 0. Зачем

Нужно разрешать конфликты, когда карту одновременно двигает юзер И программа/сервер (стянуть в
стопку, уничтожить, тасовать, abort, undo). И нужно, чтобы игрой можно было управлять из разных
источников единообразно: палец, девтулс-консоль (`window.__fd`), сервер, бот/AI, реплей. Всё это
кажется необъятным ровно потому, что смешано в кучу. Разнести на каналы — и каждый кейс простой.

## 1. Пять каналов (разделять, не смешивать)

1. **Правда (authoritative state).** Модель: слоты/порядок/значения (`board/*`, `deckRev`). ТОЛЬКО
   здесь решаются конфликты. Владелец — сервер (сейчас локальная заглушка = «локальный авторитет»).
2. **Намерения (commands).** Дискретные сериализуемые интенты: `move/shuffle/burn/abort/pick/undo`.
   Клиент их ПРЕДЛАГАЕТ (оптимистично); авторитет упорядочивает и принимает/отклоняет. Это «буфер ввода».
3. **Политика (locks/permissions).** «Можно ли командовать занятой картой», «кто может abort»,
   «можно ли пикать одну карту нескольким». Правила-как-данные; lock — лишь дефолтная политика.
4. **FX (анимации/декор).** Управляются изменением правды + явными эвентами, НИКОГДА не источник
   правды. Тасовка/тряска/ABORT_BY/сжечь/метка «кто сделал» — сюда. (`deck_fx` уже так задуман.)
5. **Presence (эфемерное).** Цветные курсоры/обводки «кто держит/смотрит»; несколько курсоров на
   одной карте. Не правда и не fx — отдельный вещательный канал (как курсоры в Figma).

### Золотое правило
Конфликты чинятся ТОЛЬКО на уровне Правды через упорядочивание команд. **Вид/анимация не дерётся
никогда — всегда уступает правде (reconcile).** Юзер тащит карту, а сервер её уничтожил → локальный
драг был оптимистичным намерением; приходит авторитетное «карты нет» → клиент отменяет драг и играет
fx «сжечь». Lock — оптимизация, чтобы уступка не была резкой (сервер по правилу не примет команду на
карту, которую ты держишь).

## 2. Ports & Adapters: один порт управления, сменные драйверы

У движка ОДИН **порт команд** (канал №2). Кто рулит — сменные **драйверы (адаптеры)** `внешний
сигнал → команда порта`: палец / девтулс-консоль / сервер / бот-AI / реплей-undo. Движок не знает,
кто за рулём. Паттерн переносится в Swift/Java (порт = протокол, драйверы = реализации) → ложится в engine-kit.

### Две РАЗНЫЕ поверхности — не путать
| | Сырой хэндл | Порт команд |
|---|---|---|
| Что | `window.__fd`, `boardZones[1].clamp(...)` | `flipCard/moveCard/setConcealed/…` (id-адресно) |
| Кто | ТОЛЬКО дев-отладка | ВСЕ драйверы: ввод, сервер, консоль-как-игрок, AI |
| Свойства | внутренности, нестабильно, dev-only | стабильный контракт, валидируется авторитетом |

Сервер общается **через порт команд**, НЕ через сырой хэндл: иначе прицепится к внутренней геометрии
вида (`clamp`) и обойдёт авторитет → вернёт связность и класс swap-бага. Консоль-дев юзает оба.

### Консоль-драйвер = forcing function
Если консоль — полноправный драйвер, эмитящий ТЕ ЖЕ команды, что сервер, ты вынужден сделать
управление = «валидируемые предложения авторитету». Отсюда бесплатно: единообразие, безопасность
(консольный «чит» = недоверенное предложение, авторитет отклонит как хакнутый клиент), тестируемость,
реплей. Консоль-драйвер по сути = ручной бот.

## 3. North-star: действия — команды, вид — функция состояния

Ключевая эволюция, в которую сходятся ВСЕ нити (swap-баг, undo, конфликты, реактивный рендер):

> **Действия — как команды (данные): `apply(state, cmd) → state'` (чисто) + отдельная эмиссия fx.
> Вид — как функция авторитетного состояния (+ fx для декора), а не ручной синк.**

- `BoardAPI` (`flipCard/moveCard/setConcealed/setCardValue`, id-адресный, БЕЗ зависимости от ввода) —
  уже зародыш порта команд. Дорастить до редьюсера.
- `refreshZoneHomes`-баг (вид синкается руками, забыли `setTarget`) — симптом отсутствия «вид = f(state)».
  Реактивный «кадр тянет вид к состоянию» убивает этот класс. См. §5.

## 4. Ответы на конкретные кейсы

- **Undo.** Feasible ТОЛЬКО если действия — команды (обратная команда / откат к чекпоинту), проходит
  через тот же авторитет+политику; «кто видит» = как у любой команды (broadcast + fx «отменил X»).
  При ad-hoc императивных мутациях (как сейчас) — откатывать нечего, тяжело. → аргумент за команды заранее.
- **Буфер ввода / порядок.** Упорядоченная очередь команд у авторитета (Colyseus уже сериализует
  сообщения по одному). Конфликт (реордер уничтоженной карты) = команда невалидна против правды →
  `action_rejected` → клиент reconcile. Клиенту нужен слой pending-команд (оптимистичная очередь с откатом).
- **Lock vs иные режимы.** Политика-конфиг; lock — дефолт, «лапать чужое» и пр. — другие политики.
- **Мульти-эвент анимация (шафл).** fx-стейт-машина на потоке эвентов (START/SET_ORDER/SPEEDUP/STOP|ABORT),
  в отличие от флипа (1 эвент → авто-стоп). Живёт в fx-канале; итоговый порядок — правда. Вариант fx:
  точный реордер (открытая/с зазором) или условный рандом-визуал (закрытая). «Загрузка над дропзоной» =
  оптимистично-неподтверждённое; presence-курсор — другим.
- **Netcode-модель.** server-authoritative state-sync + оптимистичный UI, БЕЗ lockstep/prediction-
  reconciliation (для карточно-пошагового это оверкилл — см. решение в истории). Всё выше в неё укладывается.

## 5. Что делать СЕЙЧАС vs ПОТОМ

**Сейчас (чтобы не закраситься в угол):**
- Держать механику командо-образной и state-driven; НЕ вшивать конфликт-логику в императивный движок.
- Порт (`BoardAPI`) — id-адресный, командный, без зависимости от ввода. Так и держать.
- Точечный фикс swap-бага (`refreshZoneHomes` + `setTarget`/`wake`, скип перетаскиваемой) — не мешает, делаем.

**Потом (когда появится сервер):**
- Формализовать порт команд (стабильный контракт + валидация в авторитете).
- Тонкий `window.__CROSSADE__` (реестр живых движков + порт + хелперы) — из зародыша `window.__fd`.
- Адаптеры-драйверы (ввод/сеть/консоль/AI), политика/lock, presence-канал, pending-очередь клиента.
- Рассмотреть «вид = f(state)» (реактивный синк) как устранение класса ручных-синк багов.

## 6. Открытые решения (определить по ходу)
- **Форма команды** — самый корневой кирпич (определит undo, сеть, консоль-драйвер): дискр. юнион
  `{type, ...payload}`; кто чистый редьюсер, где эмитятся fx, как адресуются цели (id-ключи уже есть).
- Держит ли клиент значение под скрытостью при сетевой раздаче (сейчас интерим — держит; secure — нет).
- Формат опакового ключа + протокол «колода ключей + частичные значения» (сервер).
- Где живёт reconcile оптимистичных команд (клиентская очередь).
