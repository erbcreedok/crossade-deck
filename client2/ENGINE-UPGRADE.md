# Апгрейд движка: новый режим игры = конфиг-МАПА, а не файл на 3000 строк

Статус: **дизайн/дискуссия** (не начато кодом). Обсуждено 2026-07-26. Дополняет `REFACTOR.md`
(секция A «Архитектура движков») конкретикой «фабрика + декларативный конфиг».

Цель: чтобы **новый режим игры** был **лёгкой мапой-конфигом (~50–100 строк данных)** + пара
чистых правил-функций, а НЕ новый императивный движок. Движок (Host) пишется ОДИН раз.

---

## 1. Диагноз: 1220 строк `playgroundEngine` — это НЕ «движок»

Если разложить файл по смыслу:

- **Generic-системы уже вынесены** (Viewport, InputRouter, SceneLayers, ElementPool, drag,
  marker, canvasHost, shadow) — переиспользуемы, «движка» в них ~0.
- **~60% файла — это СТОРИБУК**: `buildContent/buildStacks/buildPieces/buildButtons/
  buildControls/segToggle/label/blockFrame` + `testHooks`. Это демо-контент, показывающий все
  варианты. Реальный режим игры столько не содержит.
- **Остальное — «клей»**: `tick`/`render`/`shadow`, хит-тест, `inputHandlers`, `dragCtx`. Вот
  это и есть кандидат в общий **Host**.

Вывод: **новый режим ≠ новый файл на 3000 строк.** Сейчас так кажется только потому, что
песочница — витрина. Для сравнения: `tableEngine` — 367 строк, и то половина — специфика стола.

---

## 2. Целевая форма: Host (код, 1 раз) + Content (данные, на режим)

```
BoardHost        — пишется ОДИН раз. Владеет app/ticker/viewport/input/scene/pool/
(generic, код)     drag/markers + общий цикл: step → render → shadow → hitTest → gestures.
                   Ничего не знает про карты/фишки/правила.
   ▲
   │ кормится конфигом
   │
BoardConfig      — ДАННЫЕ режима («лёгкая мапа»):
(на режим, данные)   elements[], zones[], markers[], layout, rules?
   ▲
   │ собирает
   │
BoardFactory     — читает конфиг → создаёт элементы (через registry), зоны, метки, раскладку.
(код, 1 раз)       Никакого per-режим императивного build-кода.
```

Новый режим = **конфиг-файл** + (опц.) пара правил-предикатов. Движок не трогаешь.

---

## 3. Набросок «лёгкой мапы» (как это выглядит)

```ts
export const playgroundMode: BoardConfig = {
  layout: rows([                       // декларативная раскладка вместо build*()
    { title: "Карты",  cells: STORIES.map(s => ({ el: { type: "card", ...s } })) },
    { title: "Стопки", cells: [ stack("stk0", 5), stack("stk1", 5) ] },
    { title: "Фишки",  cells: [ chip(5), chip(25), chess("♞", "black"), chess("♟", "white") ] },
  ]),
  zones: [
    { name: "СЖЕЧЬ",     accepts: "burnable",  action: p => p.burn?.() },
    { name: "ПЕРЕВОРОТ", accepts: "flippable", action: p => p.flip?.() },
  ],
  markers: [
    { on: "stk0",      dragger: "grip", anchor: { icon: "anchor", when: "away"  } },
    { on: "solo-card", dragger: "grip", anchor: { icon: "ring",   when: "empty" } },
  ],
  rules: { canGrab, destroyWhen },     // маленькие чистые функции, опционально
};
```

## 4. Три опоры (всё по нашим заветам: SOLID/DRY, DIP, generic)

1. **Registry / Factory элементов.** `elementRegistry = { card, chip, chess, ... }`
   (`тип → фабрика`). Конфиг говорит `{ type: "chip", denom: 25 }`. Новый тип элемента =
   зарегистрировать фабрику, движок НЕ трогаешь. (Ровно так уже просится `Piece`.)
   Сюда же ляжет форма картиночных ассетов: фабрика берёт id ассета из конфига, а не хардкодит.

2. **Зоны по способностям, декларативно.** `accepts: "burnable"` + `action`. Драг уже так
   работает (`p.flip?.()` / `p.burn?.()`); осталось поднять это в ДАННЫЕ. Зона реагирует на
   capability-интерфейс груза, не на его тип (это уже доказано на `Piece`: «сжечь» жжёт фишку,
   «перевернуть» игнорит — фишка не `Flippable`).

3. **Правила как данные + хуки.** `canGrab` / `destroyWhen` / `onDrop` — маленькие ЧИСТЫЕ
   предикаты, инжектятся в Host. Логика режима не расползается по классу; тестируется юнитами.

---

## 5. Наследование vs композиция

- Держим **тонкий базовый `BoardHost` (общий цикл) + КОМПОЗИЦИЮ систем**, НЕ высокую иерархию
  классов. Глубокое наследование (`PokerEngine extends BoardEngine extends …`) быстро
  превращается в тот же клубок.
- Правило: **Host владеет системами; режим — это ДАННЫЕ, которые кладут в Host.** Наследование —
  только для одного шва (общий жизненный цикл/луп), как `template method`.

---

## 6. Миграция (инкрементально, TDD, ничего не ломая; каждый шаг: tsc + vitest + e2e зелёные)

1. Вынести `BoardHost` из `playgroundEngine` (lifecycle + loop + input + render + shadow + hit +
   drag + marker-glue) — механически. Песочница становится тонким потребителем. **Поведение и
   e2e не меняются.**
2. Ввести `BoardConfig` + `BoardFactory`; перегнать `buildStacks/buildPieces/zones` в
   конфиг-записи. Императивные `build*` схлопываются в данные.
3. Registry элементов + декларативные зоны + декларативные метки.
4. **Проверка делом**: написать ВТОРОЙ режим одним конфигом (напр. «шахматы» или «покер-стол»).
   Если это ~1 файл данных — цель достигнута. Затем `tableEngine` тоже переехать на Host.

Начинать: **A → потом B** (сперва чистый вынос `BoardHost` без новых фич, потом проектирование
`BoardConfig`/фабрики). Первым полигоном под конфиг — ряд «Фишки и фигуры» (`buildPieces`):
он уже декларативен по духу.

## 7. Оговорки (чтобы не переусердствовать)

- **Конфиг обязан оставаться простым** («лёгкая мапа»), иначе получим второй язык. Если поле
  требует кода — это правило, его место в маленьком чистом модуле, а не в конфиге.
- Не абстрагировать вперёд паровоза: обобщаем ровно на 2-м режиме, а не «на будущее».
- `BoardConfig` как ДАННЫЕ — задел под будущую **админ-панель** (UI редактирует конфиг:
  элементы/зоны/правила/ассеты), см. TODO в `REFACTOR.md`.
