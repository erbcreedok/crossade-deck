# Игровая зона / поле слотов — дизайн (дискуссия)

Статус: **дискуссия, кода нет.** Начато 2026-07-26. Дополняет `ENGINE-UPGRADE.md` (Content =
данные-конфиг) и `REFACTOR.md` (capability-интерфейсы, метки). Здесь копится лог решений по
«игровой зоне» (то, что пользователь сперва назвал «грид карт»).

## Итоговая модель (по ходу дискуссии)

Не «NxM-грид», а **поле слотов**. Четыре сущности:

- **`Container`** — атом. Держит членов (0..N, разнородных: карты + фишки + шахматы вперемешку),
  умеет ОТДАВАТЬСЯ (`MarkerHost`: `slotPos`/`state`/`makePayload`) и ПРИНИМАТЬ (`DropTarget`).
  Знает свои правила: `locked`, `maxSize`, `accepts`. Одиночная карта, стопка, содержимое слота —
  всё это `Container`. Конвергенция: **Стопка ≈ DropZone ≈ Container ≈ занятый слот** — одно.
- **`Slot`** — позиционированный держатель `Container` (геометрия + политика слота).
- **`Layout`** — ПОДКЛЮЧАЕМАЯ стратегия расположения слотов: `grid` / `ring` / `points` /
  `seats` / `free`. «Грид» — лишь одна стратегия.
- **`DropTarget`** — ИНТЕРФЕЙС приёма груза (не класс-зона). `bounds/accepts/verb/onDrop/priority`.
  Реализации: зона-визуал (сжечь/перевернуть), пустой слот (создать контейнер), сам контейнер
  («вышитый» глагол — дроп в стопку). Приклеивается как `withDropTarget(host, cfg)` — тот же
  attach-паттерн, что `withDragger`/`withAnchor`. Поведение кастомно через `accepts`/`verb`/`onDrop`.

Примитив = **`Board`/`SlotField`** (поле слотов). Настраивается КОМПОЗИЦИЕЙ мелких аргументов +
инъектируемые хуки на эдж-кейсы. Варианты = **ПРЕСЕТЫ** (наборы конфига / фабрики), НЕ подклассы.

```
grid          = new Board({ layout: grid() })                       // дефолт
durakGameGrid = new Board({ layout: grid(grow), slot: { maxSize: 2 }, onEmpty: "collapse" })
chessGameGrid = new Board({ layout: grid(8,8, "fixed"), background: board, addressable: true, onEmpty: "keep" })
monopoly      = new Board({ layout: ring(40), onEmpty: "keep" })
belka         = new Board({ layout: seats(), onEmpty: "keep" })
```

Эргономика «читается как имя»: пресет-фабрики поверх одного `Board` (`chessGrid()`, `durakGrid()`
возвращают `new Board(конфиг)`).

## Политика (declarative, «правила как данные» — субтипы без наследования)

```
BoardPolicy {
  layout: LayoutStrategy                 // grid | ring | points | seats | free (структурная)
  onEmpty: Action                        // СОБЫТИЕ «слот опустел» → Action; пресеты collapse/keep + кастом (напр. refill из колоды)
  slot?: { maxSize?, locked?, accepts? } // потолок стопки, заблокирован, accepts=предикат
  grow?: "none" | "cols" | "rows" | "both"
  bounds?: { minCols?, maxCols?, minRows?, maxRows?, minSlots?, maxSlots? }
  reserveNext?: boolean                  // держать место под след. слот (как play-зона)
  canPlace?(payload, slot): boolean      // создать новый контейнер в пустом слоте
  canAddTo?(container, payload): boolean // добавить в существующий ("нельзя в стопки" → false)
  makeContainer?(payload): Container     // как обернуть дроп (одиночка/стопка)
  dropInto?: boolean                     // есть ли у слотов DropTarget ("грид без дропзон")
  background?: Texture                   // кастом-фон (шахматная доска, карта настолки)
}
```

Субтипы = разные политики: «нельзя стопки» (`makeContainer` single), «нельзя в стопки»
(`canAddTo:false`), «заблокированные стопки» (`slot.locked`), «без дропзон» (`dropInto:false`).

## Лог решений

- **Q1 — адресность.** Не булев флаг-переключатель, а один примитив `Board`, настраиваемый
  композицией аргументов + хуки. Шахматы/дурак/простой = ПРЕСЕТЫ конфига, НЕ подклассы. Ядро —
  `Container`; `Board` = поле слотов, «доска» = пресет.
- **Q2 — опустевший слот.** `onEmpty` = событие→Action (пресеты `collapse`/`keep` + кастом, напр.
  refill из колоды) — per-board (разные гриды). И
  главное: абстракция шире NxM-грида — это ПОЛЕ СЛОТОВ с подключаемой раскладкой (`layout`:
  grid/ring/points/seats/free). Монополия=ring, настолка=points, белка=seats, дурак=grid+collapse.
- **Q3 — действия над группой/бордом (burn/flip/…).** Все кейсы возможны и настраиваются извне.
  Решение: действие — это первокласс **`Action`** с **политикой свёртки (fold)**, а НЕ метод-на-
  каждом-уровне. Способность (`Burnable`/`Flippable`) остаётся опциональной на АТОМЕ; над группой
  действие сворачивается по `fold`. Не все элементы обязаны иметь `burn()`.

## ПРИНЦИП: три вида настроек (ревизия knob'ов)

**Что такое knob:** именованное поле в конфиге (пропсах борда/контейнера/зоны). Для поведенческих
и предикатных knob'ов значение = **имя-ПРЕСЕТ (за ним стоит встроенная функция) ИЛИ своя кастомная
функция вместо него** — пресет это просто сахар. Для чисто структурных knob'ов значение = данные
(число/строка), переписывать нечем.

Каждая настройка попадает ровно в один вид:

1. **Структурные стратегии** — маленький закрытый набор (перечислимость по делу), НО с
   escape-hatch (можно передать свою функцию вместо пресета): `layout`, `grow`, `bounds`, `fold`,
   `grab`, `maxSize`, `priority`, `reserveNext`, `multiSelect`, `selectScope`, `dropInto`.
2. **Правила/предикаты** — функция, возвращающая да/нет/значение: `accepts`, `canPlace`,
   `canAddTo`, `resolveDrop`, `order` (компаратор), `makeContainer` (фабрика).
3. **События жизненного цикла/коллизий → `Action`** — ОТКРЫТЫЙ набор (игры придумывают исходы
   бесконечно). Каждое поле = «при событии X выполнить Action»; именованные значения — лишь
   ПРЕСЕТЫ сверху, escape-hatch всегда своя функция: `onDrop`, `onOccupied`, `onEmpty`,
   `onTransfer`, `onInvalidDrop`, `onDisplace` (куда деть вытесненную), `onBlockedInRun`.

**Итог ревизии:** то, что раньше было закрытыми enum'ами `"a"|"b"|"c"` для ИСХОДОВ (`onOccupied`,
`onEmpty`, `onTransfer`, capture-destination, blocked-in-run) — переведено в вид (3): «событие →
Action, пресеты сверху». Это ещё и УПРОЩЕНИЕ: не зоопарк ad-hoc enum'ов, а ОДИН механизм
«событие → Action» на все исходы. Структурные (вид 1) и предикаты (вид 2) — остаются как есть.

## Actions (единый механизм на все уровни)

```
Action = { name, fold, handle? }

fold:  // пресет ИЛИ своя reduce-функция (escape-hatch)
  "all"       — применить, только если ВСЕ члены умеют; иначе no-op → домой  (нынешний flip пачки)
  "each"      — применить каждому, кто умеет; неумеющих пропустить           (нынешний burn пачки)
  "container" — выполняет САМ контейнер/борд (один эффект на всё); членам способность НЕ нужна
  "block"     — запретить (verb не показывается, груз домой)
  (fn)        — своя свёртка: напр. «применить top-down пока не откажет», «к N случайным»
```

- **Где объявляется (все три, по областям, единообразно):** `DropTarget` предлагает Actions + их
  `fold`; `BoardPolicy` — дефолты для слотов/контейнеров; **дирижёр (движок) ТУПОЙ** — только
  маршрутизирует (спрашивает цель «примешь?» → «сделай»), burn/flip не хардкодит.
- **Один уровень, разный scope:** `element.burn` (атом) → `container/stack` (Action, свёрнутый по
  членам) → `board` (тот же Action в области борда). «Приклеить `Burnable` на борд» = дать борду
  `container`-fold Action; унифицировано со стопкой (центральный слот борда — тоже `Container`).
- **Прецедент:** `onDrop: p => p.burn?.()` уже есть; `p.burn?.()`/`p.flip?.()` = fold `each`/`all`
  на уровне payload (`GroupDrag`). Поднимаем это в именованную настраиваемую политику.
- **Кейс «Кидай и сжигай»:** центр = `DropTarget{ accepts: ()=>true, action: burn(fold) }`, где
  `fold` = `each` (горят только горючие) / `container` (борд жрёт всё одним огнём) / `all` (блок,
  если есть негорючее) — выбор конфигом, без хардкода.

## Эдж-кейсы

**EC1 — приоритет `DropTarget` при перекрытии (решено).** Дефолт-резолвер: собрать все цели, чьи
`bounds` накрыли точку И `accepts(payload)===true`, отсортировать и взять первого:
`priority (desc) → вложенность (глубже=специфичнее) → z-index (topmost)`.
- Внутреннее побеждает внешнее (стопка → слот → борд), как всплытие в DOM.
- `accepts=false` = ПРОЗРАЧНОСТЬ: цель выпадает, палец проваливается на следующую (никогда не
  «съедает» дроп молча). Заблокированный/полный слот так же пропускает груз дальше или домой.
- Ховер подсвечивает ПОБЕДИВШУЮ цель + её `verb`; хит-тест по НЕсдвинутой сетке (соседи
  расступаются визуально, но цель не дрожит под неподвижным пальцем).
- **Переопределяемо:** `priority` на цели (тайбрейк) + хук `BoardPolicy.resolveDrop?(candidates,
  payload)` — целиком заменяет дефолтную иерархию.

## Терминология (принята пользователем)

**фигура** = любой перемещаемый элемент (карта, фишка, шахм. фигура). **стек = стопка =
контейнер = борд** — ОДНО поведение, разный *scope* (уровень хранения/контроля). Механику желаем
единую и настраиваемую схоже на всех уровнях.

## Перемещение фигур (drag / drop / reorder / swap) — ядро

Груз драга = **временный `Container` (1..k фигур), кочующий между source и target**. Цикл:
GRAB → source реагирует (`n−k`, `onEmpty`) → CARRY (идентичность сохранена, спрайты летят) →
TARGET (резолв EC1 + `accepts`) → COMMIT. Всё — те же `GroupDrag`/метки/`DropTarget`, единообразно.

**GRAB — что берём (knob `grab`, можно несколько; зависит от ПОДАЧИ контейнера):**
- `top` — только верх (ужатая «рука», закрытая стопка, сброс).
- `any` — любую по позиции (открытый веер).
- `run` — саб-ран `i..верх` (солитёрный «хвост»; удобен и для стека фишек).
- `whole` — вся пачка за грип-метку (уже есть).
- escape-hatch: своя `grabSelector(container, hitIndex) → id[]` (напр. «все того же ранга/масти»).
- Некоторые фигуры **заблокированы для драга** (`draggable:false`). Если такая попала в `run` —
  событие **`onBlockedInRun` → Action** (пресеты: выброс-и-селект / отмена, с анимацией или без; или свой исход).

**COMMIT на ЗАНЯТЫЙ слот — событие `onOccupied` → `Action`** (открытый, не enum). Пресеты:
- `merge` — груз ложится ПОВЕРХ целевого стека (дурак/солитёр);
- `swap` — меняются местами (target предпоказывает себя при ховере);
- `capture` — цель вытесняется, новичок занимает слот (шахматы: конь съедает пешку);
- `reject` — занятый слот отказывает.
- Игра может дать СВОЙ исход (собрать в мельд, «бой» с сравнением, отскок и т.п.).
- Вытеснение (`swap`/`capture`) само вызывает событие **`onDisplace` → Action**: куда деть
  вытесненную фигуру (за борд / в сброс / в слот / кастом). «Пешка за доску» = `capture` + `onDisplace`.

**Ховер-фидбек:** соседи в дропзоне УСТУПАЮТ место под будущий индекс новичка (playHover); при
`swap` — target предпоказывает обмен. Хит-тест по НЕсдвинутой сетке (без дрожи).

**REORDER внутри одного контейнера — тот же механизм** (source=target): вставка на позицию `j`
(из зазора веера), не только «верх».
- Открытая стопка карт → реордер вкл.
- Закрытая → реордер при драге ВЫКЛ по умолчанию; но игра может включить (перемещение в закрытой
  стопке — «зум + тонкие пальцы»). Всё knob'ом, чтобы в другой игре не пытались.

## Мультиселект (несмежный набор фигур)

Смежный `run` (`i..верх`) — простой, отдельно. Несмежный мультиселект — явный РЕЖИМ:

- **Вход в режим:** кнопка «вкл режим выделения» (универсально, обе платформы; в песочнице —
  демо-кнопка) + long-press по фигуре (тач-шорткат). **Выход:** клик/tap вне зоны и т.п.
- **В режиме:** ховер по фигуре → подсветка (ДЕСКТОП-плюшка, на тач ховера нет); нажатие/клик →
  тоггл в наборе; начал драг по выделенной → весь набор слетается в один стек и летит **за
  пивотом** (пальцем). Драг по невыделенной → обычный single/run (`keep|clear` выделения — knob).
- **Дроп «в никуда» (невалидная цель) — `onInvalidDrop` = ОТКРЫТЫЙ `Action`, не enum.** Пресеты
  для удобства: `keep` (вернуть, выделение сохранить) / `clear` (вернуть + сбросить) / `error`
  (отказ с фидбеком). Но по сути туда можно повесить ЛЮБОЙ Action — `burn` набора, кастомный
  «раздать по игрокам», «вернуть в колоду» и т.д. Игра регистрирует свой Action — движок не трогаем.
- **Кнопка «отменить выделение»** — видна ТОЛЬКО в режиме выделения, гасит набор.
- **Состояние:** `selection: Set<id>` — транзиентное UI-состояние контейнера/борда (не игровая
  правда). `multiSelect: on|off` по контейнеру, дефолт off.
- **Область выделения — knob `selectScope: "container" | "board"`** (по контейнеру/игре). `board`
  = меж-контейнерный (собрать из разных стопок/зон, каждая фигура знает свой дом → возврат/`n−k`
  по своим источникам). В песочнице демо ОБОИХ типов.
- **Порядок несомого/сливаемого набора — `order` = компаратор с пресетами** `"source"` (как
  расставлены в руке/пиле заранее) / `"selection"` (как тыкал → очередь) + возможность своей
  функции (по рангу, козыри вниз и т.п.). Дефолт: `source` для одного контейнера, `selection` для
  меж-контейнерного. (По принципу «что сделать = открытый хук».)

## Кейсы, которые дообсудить (добавлено сверх сказанного пользователем)

- **REORDER = insert-at-`j`**, а не только «верх»: COMMIT считает индекс вставки из точки дропа
  (веер → зазор; закрытый стек → только верх/выкл). Уже заложено выше, но это отдельный knob.
- **Facing при переносе**: карта из закрытой стопки (рубашкой) в открытую зону — раскрывается?
  Зависит от секретности (`REFACTOR.md` C3): событие **`onTransfer` → Action** (пресеты
  reveal/keep/conceal + кастом, напр. «раскрыть только владельцу»).
- **Мульти-селект НЕсмежный** vs смежный `run`: брать НЕсколько произвольных фигур (не хвост)?
  Отдельный режим `select` поверх `grab`.
- **Auto-spread/auto-open** закрытого/ужатого стека при ховере — временно раздвинуть для прицела
  (помогает «тонким пальцам»); knob.
- **`draggable` ≠ `targetable`**: фигура может быть не-таскаемой, но валидной целью (и наоборот) —
  два независимых флага.
- **Порядок при merge** — это тот же `order`-компаратор (см. Мультиселект), НЕ отдельный knob.
- **Move = транзакция**: remove(source)+add(target) атомарно; отказ на любом шаге → ничего не
  меняется, груз домой (с анимацией/без — knob).

## План (TDD, когда закончим дискуссию)

Чистые модули сперва: `boardModel` (слоты↔контейнеры), `layout/*` (grid/ring/points), `dropTarget`,
`slotPolicy` — юниты. Потом визуал в песочнице + e2e. Ложится как `Content` в `BoardFactory`
