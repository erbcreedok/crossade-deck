## 1. Словарь (сведение терминов, «мб я путаю»)

- **Фигура** — любой перемещаемый элемент: карта, фишка, шахматная фигура, тайл
  (GRID-DESIGN, принято владельцем ранее).
- **Контейнер** — атом хранения (1..N фигур): одиночка, стопка, содержимое слота.
- **Слот** — позиционированный держатель контейнера; **раскладка** — стратегия расстановки
  слотов (grid / ring / hex / pile / linear / free). «Грид» — лишь одна из раскладок.
- **Поле слотов** (`SlotField`, в коде `game/slotfield/*`; до 2026-08-03 называлось `board/*` — переименовано, чтобы освободить слово Board) — примитив «слоты + политики приёма». Владелец прав, что
  «гриды живут обособленно и ближе к стеку»: поле слотов и стопка — одно поведение разного
  scope (конвергенция из GRID-DESIGN).
- **БОРДА / `Board`** (в коде — `BoardSpec`, слой `game/boards/`) — то, что просил владелец:
  самостоятельная СБОРКА стола: несколько зон (у каждой — СВОЁ поле слотов со своей
  раскладкой), места игроков, панель действий, смарт-мок вместо правил. Дурак, шахматы,
  монополия, крестовый — борды. Это разворот `BoardConfig` из ENGINE-UPGRADE.md, дополненный
  местами и действиями.
- **Место (Seat)** — стул за бордой. **Комната (Room)** — сборка юзеров вокруг борды (§6).

Итого иерархия: фигура → контейнер → слот → поле слотов (зона) → **борда** → комната.

## 2. Разведка кода: что есть, паттерны и швы

Полная карта — **`docs/BOARDS-ANALYSIS.md`** (разведка 2026-08-03: все модули `slotfield/*`,
`slot/*`, `kit/*`, сцены, 13 швов). Здесь — то, что решает дизайн:

**Опорные паттерны (доказаны кодом):** правила/рычаги как данные (`FIELD_PRESETS`,
`STACK_LAYOUTS`, `BUTTON_ROWS`…); стратегия вместо подкласса; способности вместо типов;
одно дерево на рендер и дроп; механика ⟂ отрисовка (логика без Pixi); общий слой вместо
копии (`SceneEngine`, `SectionContext`); choke-point действий; rest/armed/hot; фикс-доска +
камера; локальный мастер вместо сервера (`multiplayer/localTable.ts`).

**Главные факты, меняющие план:**

1. **Систем раскладки ДВЕ, и «витринная» проиграла бою.** `slotfield/fieldZone.ts`
   (onOccupied/capture/AcceptRule) не используется НИ ОДНОЙ игрой — только песочницей и
   сторибуком. Все три игры живут на дереве `slot/` (у которого зато НЕТ
   onOccupied/swap/capture). Контракт борды обязан их слить, а не родить третью систему.
2. **Канон уже существует — Косынка.** Она гибрид: СОСТОЯНИЕ на `slotfield/slotField.ts`+`Container`
   (чистые иммутабельные переходы), ГЕОМЕТРИЯ на дереве `slot/`. Это и берём каноном борды
   (§4): состояние — `slotfield/*`, вид/дроп — дерево.
3. **FieldPreset покрывает только доску.** Ни мест, ни ролей, ни кнопок, ни словаря ключей
   зон (хардкод "deck"/"play:N"/"seat:ID"/"r,c"). Кнопки действий и права на драг — везде
   императивные ветвления в сценах (единственное место, где «правила как данные» нарушены).
4. **Портов команд три несовместимых** (`Command` стенда, `CrossadePort` игр,
   `SolitaireAction`) — ни один не сериализуем и не покрывает «кнопку борды».
5. **Место игрока — костыль** (пустая group с pile, потому что dropTarget не спускается в
   листья), подача мест — три разных вида (лейбл+счёт / лейбл / рубашки-alias).
6. **Система B (selection/assembly/pileIdentity/dropPolicy) в играх не используется** —
   в каркас v1 её НЕ тянем: сначала борды, мультиселект подключим, когда попросит игра.
7. Ловушки по мелочи: `asFlippable` смотрит на метод, а не флаг (issue #103); два «ранга»
   (A=14 и A=1) в одной папке; «дропзона» — два понятия (зона-ДЕЙСТВИЕ и зона-МЕСТО) —
   в контракте различаем явно.

## 3. Смарт-моки: что это значит здесь

Смарт-мок = **драйвер порта команд без валидации правил**. Всё, что борда умеет, выражено
командами; мок честно их исполняет, ничего не запрещая сверх политик зон (maxSize, accepts
по способностям). Отсюда:

- перемещение фигур руками — свободное, в рамках политик зон (как в песочнице);
- кнопки («раздать», «собрать», «след. круг», «бросить кубики») — НЕ правила, а макро-команды
  мока: раздать = серия `move` из колоды по местам; никакой проверки «можно ли»;
- выбытие/победа/очередность — индикация, не запрет: мок может подсветить «чей ход»
  (по кругу, направление — кнопкой), но не мешает ходить вне очереди;
- когда придут настоящие правила — они встанут МЕЖДУ портом и мутацией (авторитет,
  CONTROL-DESIGN), команды и борда не изменятся.

**Где живут кнопки (решение):** действия — это интенты, а не предметы стола, поэтому:
- **действия борды** (раздать, собрать, перемешать, след. круг, направление) — нижняя
  канвасная панель действий (ActionBar, родня TopBar), принадлежит борде;
- **действия зоны** (собрать кучу, открыть веер) — глагол у самой зоны (verb дроп-цели,
  как «сбросить»/«взять» в макете) или её метка;
- **действия места** (сесть/встать/поменяться) — на самом месте (тап по стулу).

## 4. Контракт борды (`BoardSpec` — данные + маленькие чистые хуки)

```ts
BoardSpec {
  id: string                       // "chess" | "krestovyi" | "monopoly" | …
  title: string
  elements: ElementDef[]           // из registry: card | chip | piece(kind) | tile — данные, не классы

  zones: ZoneSpec[]                // общий стол: у КАЖДОЙ зоны своё поле слотов
  seats: SeatsSpec                 // места игроков
  hand?: HandSpec                  // личная рука (есть не у всех борд: у шахмат нет)
  actions: ActionSpec[]            // панель действий борды (мок-команды)
  mock: MockSpec                   // сценарий смарт-мока: раздача, начальная расстановка
}

ZoneSpec {
  id: string                       // "field" | "discard" | "chain" | "chance" | …
  layout: LayoutSpec               // grid(cols,rows,fixed?) | ring(n) | pile | linear | free
                                   //   — «у бордов есть свой грид расстановок; бывают зоны с
                                   //     отдельными гридами» — ровно это
  policy: {                        // GRID-DESIGN BoardPolicy, поднабор
    onOccupied: "merge"|"swap"|"capture"|"reject" | fn
    maxSize?, accepts?, dropInto?, reserveNext?, onEmpty?
  }
  background?: string              // ассет: шахматная доска, поле монополии
  shared: boolean                  // публичная (координаты общие, жесты транслируются)
}

SeatsSpec {
  count: { fixed: n } | { min, max }   // шахматы fixed 2; крестовый 2..8; динамика = on-run join
  layout: "row" | "ring"               // как места стоят вокруг стола
  show: "backs" | "count" | "chips" | "none"  // подача чужого места (live-руки / счёт / стек фишек)
  swap: boolean                        // можно ли меняться местами («сесть за стул»)
}

ActionSpec { id, label, scope: "board" | zoneId, command: MockCommand }
MockSpec   { deal?: { from: zoneId, each: n | "all-even-dealer-last", to: "hands" | zoneId },
             setup?: PlacementRule[] }   // начальная расстановка (шахматы: фигуры по клеткам)
```

**Реализация — по канону Косынки (гибрид, см. §2 п.2):**

- **Состояние** — `slotfield/slotField.ts` + `Container` (чистые переходы place/move/remove); ключи
  слотов — ЕДИНЫЙ словарь `ZoneKey` (`zone:slot`, напр. `field:r3c4`, `chain:2`, `seat:p2`) —
  закрывает шов «хардкод строк в каждом дереве».
- **Геометрия/дроп** — ОДНО дерево `slot/*`, каждая зона — поддерево со своей раскладкой;
  `ring`/`hex` из `slotfield/layout` подключаются стратегиями absolute-координат внутри поддерева.
- **Политики приёма** (`onOccupied: merge/swap/capture/reject`, `AcceptRule`) — поднимаются из
  `slotfield/fieldZone.ts`/`slotfield/dropResolve.ts` (написаны и покрыты) и вешаются на `caps.drop`
  поддеревьев — так `slot/` получает недостающие onOccupied/capture, а BoardZone перестаёт
  быть системой-соперницей и становится набором чистых правил. Зоны-ДЕЙСТВИЯ (сжечь/
  перевернуть) остаются `ui/DropZone` — это другое понятие, в контракте различены.
- **Место (Seat) — первокласс** дерева (не «группа, притворяющаяся прямоугольником»):
  свой узел с подачей `show` и хит-областью «сесть».
- **Команды** — ЕДИНЫЙ мок-порт борды (сериализуемый юнион: `move`, `deal`, `shuffle`,
  `turn`, `sit/stand/swap` …), кнопки ActionBar и палец — два драйвера одного порта
  (CONTROL-DESIGN). Существующие три порта не размножаем: порт борды — кандидат на их
  постепенное слияние, но в v1 трогаем только своё.
- `BoardScene extends SceneEngine` — ОДНА, generic; конкретная борда — только данные+хуки.

Мультиплеер НЕ обязателен: борда живёт standalone на одном канвасе. Кто исполняет команды —
шов `BoardDriver` (driver.ts): localDriver (смарт-мок под сценой) или клиент общего мастера
`boardTable.ts` (N клиентов, одно авторитетное состояние, latency на оба плеча) — стори
«Mechanics/Boards → Live». Реальный сервер — замена boardTable, сцены и борды не меняются.

## 5. Три контрастных примера (первая волна)

### 5.1 Шахматы — константные места, адресный грид, наблюдатели

```ts
chess: BoardSpec = {
  elements: PIECES,                       // registry: piece("♟","white") …
  zones: [{ id: "field", layout: grid(8, 8, "fixed"), background: "chessboard",
            policy: { onOccupied: "capture", onDisplace: "offboard" }, shared: true }],
  seats: { count: { fixed: 2 }, layout: "row", show: "chips", swap: true },
  actions: [ resetSetup, flipBoard ],
  mock: { setup: CHESS_START },           // расстановка — данные
}
```
Контраст: нет руки и колоды; фигуры вместо карт; capture с выносом за борт; фиксированные
места + наблюдатели (роли, §6) + опция «мешать» = политика «наблюдатель может двигать».

### 5.2 Крестовый — карточный, цепочка, динамические места

```ts
krestovyi: BoardSpec = {
  elements: DECK_36,
  zones: [
    { id: "chain",   layout: linear({ grow: true }), policy: { onOccupied: "merge" }, shared: true },
    { id: "discard", layout: pile, policy: { onOccupied: "merge" }, shared: true },
  ],
  seats: { count: { min: 2, max: 8 }, layout: "ring", show: "backs", swap: true },
  hand: { reorder: true },
  actions: [ dealAllEven,                  // вся колода поровну, дилеру последним → у него меньше
             nextTurn, reverseDirection,   // ход по кругу, направление меняемо (индикация)
             takeChain, chainToDiscard ],  // «беру» (цепочка в руку) / «в сброс» (закрыт круг)
  mock: { deal: { from: "deck", each: "all-even-dealer-last", to: "hands" } },
}
```
Контраст: динамические места, ЦЕПОЧКА как зона (карты ложатся вереницей, не кучками),
две общие зоны, «чей ход» — бегущий индикатор по кругу (мок, не запрет). Правила отбоя
(6 бьётся 8, взял — круг не закрыт…) НЕ кодируются — это живёт в голове игроков, борда лишь
даёт им честный стол: цепочка, руки, сброс, раздача, круг.

### 5.3 Монополия — ring-раскладка, свой фон, фишки + деньги

```ts
monopoly: BoardSpec = {
  elements: [ ...TOKENS, ...MONEY_CHIPS, ...CARDS_CHANCE, ...CARDS_TREASURY, DICE ],
  zones: [
    { id: "track",    layout: ring(40), background: "monopoly", policy: { onOccupied: "merge" }, shared: true },
    { id: "chance",   layout: pile, policy: { onOccupied: "merge" }, shared: true },
    { id: "treasury", layout: pile, policy: { onOccupied: "merge" }, shared: true },
  ],
  seats: { count: { min: 2, max: 6 }, layout: "row", show: "chips", swap: true },  // деньги у места
  actions: [ rollDice, dealMoney ],       // кубики = мок-рандом с анимацией; банк раздаёт стартовые
  mock: { setup: TOKENS_AT_GO, deal: { from: "bank", to: "seats" } },
}
```
Контраст: кольцо со СВОИМ фоном-картой, смешанные элементы (фишки+карты+кубики+деньги),
у мест не рука, а видимое имущество (стек фишек-денег).

### Вторая волна (реализована 2026-08-03: `game/boards/library/` — файл на игру)

- **Дурак**: grid-зона пар атака/защита (`maxSize: 2`), козырь под колодой, `onEmpty: collapse`.
- **Белка**: без колоды, seats-раскладка, взятки стопками у мест.
- **УНО**: пил сброса с «активным цветом» (метка зоны), направление хода — уже есть у крестового.
- **Манчкин**: два пила (двери/сокровища) + «шмотки» у места (зона места с гридом! — тест
  тезиса «зоны с отдельными гридами у мест»).
- **Покер**: борд 5 слотов, банк-зона фишек в центре, блайнды — маркеры мест.
- **ДнД**: hex/grid поле с фоном-картой, разнотипные фигуры, кубики; свободная зона мастера.

## 6. Роли (Юзер / Игрок / Гость / Наблюдатель / Модератор)

Роли — не иерархия классов, а **три ортогональных факта** о человеке:

```
Identity (кто):    User  = токен аккаунта
                   Guest = токен без аккаунта; имя = «цвет + зверь» («красная панда»,
                           «жёлтый верблюд»), presence-цвет = цвет из имени
Membership (где):  member | moderator            — отношение человек × КОМНАТА
Occupancy (за чем): player(seatId) | observer    — отношение человек × БОРДА
```

- **Игрок** — не сущность, а человек, ЗАНЯВШИЙ место (`player(seat)`). Встал — снова
  наблюдатель. «Поменяться местами» = транзакция у авторитета: освободить+занять двумя
  сторонами (или swap по согласию — политика комнаты).
- **Наблюдатель** видит стол как игрок без места: публичные зоны полностью, чужие руки
  рубашками (alias — уже построено в live-режиме). «Мешать» (шахматы) = политика
  `observersCanTouch: true` — наблюдателю разрешается драг в shared-зонах.
- **Модератор** — членство в комнате: смена борды, кик, политику крутит. В комнате без
  модерации — таких прав нет ни у кого (или у всех — политика).
- Динамические места = join on-run: свободный стул виден всем, тап — сел (если seats
  не fixed-и-заняты). Presence-цвет у КАЖДОГО (и наблюдателя тоже) — обводки жестов уже
  работают в live-режиме.

Всё это — данные `RoomPolicy`, не ветки кода: `observersCanTouch`, `swapNeedsConsent`,
`guestsAllowed`, `moderated`.

## 7. Комнаты (продумано по просьбе владельца; примеры ниже)

**Комната = сборка людей вокруг живой борды.**

```ts
Room {
  id, code                          // код входа — как inviteCode сейчас
  members: { identity, membership, occupancy, color }[]
  board: { spec: BoardSpec, state: BoardState }   // ТЕКУЩАЯ борда — заменяемая
  policy: RoomPolicy                // guestsAllowed, observersCanTouch, swap, moderated…
}
```

**Ключевое решение — «и так и так» у владельца сходится в одну модель:**
стандалон-игра и комната — НЕ два режима кода. Стандалон = **неявная комната** с одной
фиксированной бордой и спрятанным комнатным UI (ровно как Crossade сейчас создаёт комнату по
коду, просто не называет её). Тогда:

- роут `/v2/chess` → создать анонимную комнату { board: chess, UI комнаты скрыт };
- «комната с выбором игр» → та же комната, но с лобби-панелью «сменить борду»;
- **смена борды** = замена `board.spec` (+ сброс/миграция state) — люди, роли, цвета,
  presence остаются; это дёшево, потому что борда — данные (§4);
- «навесить правила» (будущее) = вставить валидатор между портом команд и мутацией,
  комнату и борду не трогая (CONTROL-DESIGN, канал Политика).

**Слои ответственности** (кто чем владеет):

```
Room     — люди, роли, политика, КАКАЯ борда стоит
BoardSpec— какой стол собрать (данные)
BoardScene — как это выглядит и тащится (одна, generic)
MockDriver / (потом) сервер — кто исполняет команды
```

### Примеры комнат

```ts
// 1. «Пятница» — компанейская, гости, динамика
{ code: "5246", policy: { guestsAllowed: true, moderated: true },
  board: krestovyi,
  members: [ userYerbol(moderator, player@seat1), guest("красная панда", player@seat2),
             guest("жёлтый верблюд", observer) ] }

// 2. Шахматный стол — константа мест, зрители, «мешать» выключено
{ policy: { observersCanTouch: false, swapNeedsConsent: true },
  board: chess,
  members: [ userA(player@white), userB(player@black), 5 × observer ] }

// 3. Тот же стол, вечер удался — «мешать» включили
{ policy: { observersCanTouch: true }, board: chess, … }

// 4. Стандалон-монополия (роут без кода комнаты)
{ implicit: true, policy: { guestsAllowed: true }, board: monopoly,
  members: [ guest("синий енот", player@seat1) ] }   // UI комнаты не показывается

// 5. Смена игры на лету: комната №1 голосует «в УНО» → board.spec = uno,
//    state пересобран моком (раздача заново), места и цвета сохранены.
```

Локальная реализация для сторибука: **расширение `localTable.ts`-мастера** — те же каналы
