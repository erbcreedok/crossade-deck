## A. Отложенные решения (ждут выбора)

1. **Канвас-слайдер vs Stepper.** Числовые контролы на `/motion` — это `Stepper` (−/+, целые
   шаги), т.к. канвас-примитива «плавный слайдер» нет. Из-за этого дробные шаги (напр. дрожание
   0.1) огрубились до целых. Открыто: сделать ли отдельный UI-примитив «слайдер» в канвасе.
2. ~~**Какой ОДИН вариант цензуры идёт в прод.**~~ РЕШЕНО: «TG-пыль» (частицы) — дефолтный вид
   скрытой карты. Дефолт-рычаги (частица 5 / свапы 25 / дрожание 1 / частота 1, мерцание выкл,
   пыль замедлена ×3) вынесены в `censorConfig.ts` — один источник правды для стенда и доски.
   Остальные 3 (CPU-мозаика, GPU-remap, GPU-pingpong) остаются на стенде как «анимации фигур для
   других кейсов» / dev-сравнение.
3. **Плотность частиц как рычаг.** Реальная цена частиц — их КОЛИЧЕСТВО (не size/freq). Ползунка
   «плотность» по-прежнему нет, но постановка с 2026-08-02 сместилась: у пыли теперь ДВА разных
   источника, и рычаг нужен обоим или ни одному.
   - Стенд `/motion` (`censorDemo.particleCard`): `step = 4`, `perCell = 2` — как и было.
   - Карта на столе (`engine/censorSource.ts`): облако строится из настоящего лица, и количество
     уже не константа — плотность взвешена по непохожести клетки на общий тон карты (`INK_GAIN`,
     `INK_FLOOR`) и сверху срезана `MAX_POINTS = 900`.
   То есть «плотность» для карты — это не один множитель, а тройка (шаг сетки, порог отсечки,
   потолок). Ползунок, крутящий только `step`, соврёт: на светлой карте он не изменит ничего,
   потому что решает отсечка. Сначала решить, ЧТО именно называется плотностью.

9. ~~**БАГ: «сжечь» не догорает.**~~ ✓ ИСПРАВЛЕНО 2026-08-02: фронт горения перелетает верхнюю
   кромку на амплитуду волны (`BURN_WAVE`), три регрессионных теста. Ниже — исходный разбор.

   Записано
   2026-08-02 по наблюдению владельца. Причина, судя по коду, арифметическая и лежит в
   `src/game/effects/burn.ts::burnFrame` (чистая функция, есть тест `burn.test.ts`, 5 кейсов):

   ```
   const frontY = -TEX_H / 2 + TEX_H * (1 - p);            // при p=1 фронт РОВНО на верхней кромке
   pts.push(x, frontY + Math.sin(...) * TEX_H * 0.05);     // но фронт ВОЛНИСТЫЙ, ±5 % высоты
   ```

   Полигон маски — «видимая верхняя часть». Его верхняя кромка прибита к `-TEX_H/2`, а волнистый
   фронт колеблется вокруг `frontY`. При `p = 1` фронт совпадает с кромкой, и там, где синус
   ПОЛОЖИТЕЛЕН, фронт оказывается НИЖЕ кромки — остаётся видимая полоска высотой до `0.05·TEX_H`,
   зубчатая по форме волны. Ровно то, что видно глазами.

   Лечение: фронт должен ПЕРЕЕЗЖАТЬ верхнюю кромку минимум на амплитуду волны, чтобы при `p = 1`
   полигон гарантированно вырождался. Амплитуда сейчас зашита числом `TEX_H * 0.05` в двух местах
   смысла — вынести в константу и использовать её же в вылете.

   Регрессионный тест (чистый, без Pixi): при `p = 1` ни одна точка фронта не лежит ниже верхней
   кромки. Без него правка «на глаз» вернётся при первой смене амплитуды.
