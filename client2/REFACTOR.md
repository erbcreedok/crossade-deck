## 0. Принцип

Один сквозной принцип на всё: **тонкое ядро + отделяемые способности**. Применяется
одинаково к движкам (хост + системы) и к элементам (вид + capability-интерфейсы + эффекты).
Всё зависит от ИНТЕРФЕЙСОВ, а не от конкретного `Card` (DIP). SOLID/DRY.

Что это даёт:
- лепить новые движки из кусков старого;
- заменить карту на любой элемент (фишка, стопка, шахматная фигура) — драг/планы/тени/физика
  продолжают работать;
- разделить идентичность и значение карты → будущая серверная секретность.

## A. Архитектура движков (композиция)

Форма: **Host (база) + Системы (has-a) + Контент**.

- `BaseCanvasEngine`/`Host` — владеет только Pixi: app, тикер, wake/sleep, ресайз, ожидание
  шрифтов, диспетчер pointer/wheel, mount/teardown. Про карты не знает.
- Системы (композиция, ортогональны): `Viewport`, `SceneLayers`, `ShadowPass`, `ElementPool`,
  `InputRouter`.
- Game-features (композиция): `DropZones`, `EdgeScroll`, `BoardAPI`, `Effects`.
- Контент — единственный, кто знает «это песочница/стол/меню».

Движок = Host + выбранные системы + контент:
- Menu = Host + Buttons + Effects(shout).
- Sandbox = Host + Viewport + Input + Pool + Layers + ShadowPass + Zones + BoardAPI +
  EdgeScroll + SandboxContent.
- Table = то же ядро + TableContent (разница только в контенте).

Граф зависимостей (что живёт без чего):
- Слой 0 (чистый, уже изолирован): spring, CardBody, anim, card, cardTextures, pipLayout,
  cardBack.
- Слой 1 (Pixi-примитивы, взаимно независимы): Host, Viewport, SceneLayers, ShadowPass.
- Слой 2 (домен): интерфейсы элементов; ElementPool (зависит от интерфейсов + SceneLayers;
  НЕ от Viewport/Input). Обобщение нынешнего `TablePool`.
- Слой 3 (фичи): InputRouter (Host + Viewport[опц.] + хит-тест по интерфейсам); DropZones,
  EdgeScroll (мосты над InputRouter/Viewport); BoardAPI (ТОЛЬКО ElementPool по id — без
  Viewport/Input, значит серверные анимации работают без ввода).
- Слой 4 (контент): Sandbox/Table/Menu-content.

Наследие vs композиция:
- Наследие — только оболочка, мелко: `BaseCanvasEngine` + хук `buildScene()` (template method).
- Системы — композиция (`has-a`), регистрируются в хосте.
- Элементы — интерфейсы + композиция поведений, НЕ дерево классов.

## B. Модель элемента (интерфейсы)

`TableElement` (id, body, plane/state, sync, step) + мелкие capability-интерфейсы (ISP):
`Draggable`, `Flippable`, `Concealable` (скрытость), `Burnable`, `ShadowCaster`, `HasBody`,
`HasPlane`. Системы зависят от них, не от `Card`.

- **Состояние — снаружи.** Стол/движок задаёт «план» элемента и там же им управляет; элемент
  не авторитет по своему состоянию (внутренний стейт можно оставить опцией, не источником
  правды). Маппинг «состояние → вид» (масштаб/тень) вынести из элемента.
- `Card` = тонкий ВИД (текстуры/лицо/переворот), реализует подмножество интерфейсов.
  `Chip`/`ChessPiece` — другие реализации.
- Эффекты (burn/dissolve) — прикрепляемые поведения, не ветки `SpecialCard extends Card`.

## C. Карта: идентичность, значение, кастом, скрытость

**C1. Ключ ≠ значение.** Каждая карта уникальна и имеет серверный **шифр-ключ** (наш `Card.id`,
роль растёт до опакового токена, из которого нельзя вывести значение). Ключ известен всегда,
по нему адресуют/анимируют/трекают. **Значение** (ранг/масть/кастом) — отдельные данные, могут
быть придержаны сервером; раскрытие = сервер сопоставляет ключ→значение. Уникальность по ключу,
не по виду. В песочнице клиент ПОКА знает значение (временно), потом — только сервер.

**C2. Кастомность (убрать `joker`).** `joker` — захардкоженный частный случай (флаг + ветка →
`jokerFace()`). Убрать: лицо/содержимое кастомной карты задаётся снаружи (дескриптор/фабрика/
текстура — форму выбрать при реализации). Карта может быть чем угодно вне «ранг+масть»: без
номинала/масти, 14-й ранг, 5-я масть, «визит к доктору». Джокер — просто один экземпляр кастома.

**C3. `hidden` — режим секретности, не «лицо 🖕».** Сейчас `hidden` подменяет лицо на мозаику
🖕. Неверно. Скрытость — РЕЖИМ, прячущий значение реальной карты (у неё есть истинная
идентичность), даже при перевороте (переворот не течёт). Видимое в скрытом виде — маскирующая
заглушка (🖕/рубашка/конфиг — может быть кастом-лицом из C2), не настоящее лицо. Включается/
снимается ИЗВНЕ (хендлеры игры/сервера): `reveal`/`setHidden(id,false)` — операция `BoardAPI`.
Карта функционирует БЕЗ известной идентичности (придержана) — значение приходит при раскрытии.
Кейс: раздача колода→рука, по прилёте игра снимает скрытость и показывает карту.

## E. Порядок работ (поэтапно, без поломок; каждый шаг: tsc + тесты + визуал в Playwright)

1. Выделить `BaseCanvasEngine`/Host — убрать DRY-дубли жизненного цикла/ввода (механически, low-risk).
2. Вынести системы `Viewport`, `InputRouter`, `SceneLayers`+`ShadowPass` из freeDeskEngine (композиция).
3. Ввести интерфейсы элементов; `Card` реализует их; управление состоянием — наружу.
4. Обобщить `ElementPool` (из `TablePool`); песочницу перевести на него.
5. Модель карты: разделить ключ/значение (C1); кастом-лица, убрать `joker` (C2); режим `hidden` (C3).
6. Sandbox-секции → декларативный контент; вынести эффекты.
7. `tableEngine` на общие куски (контент над Pool + tableLayout + общий Input).

## E-bis. Метки (`marker.ts`) — сделано

`withDragger`/`withAnchor` (императивные «HOC»): одна абстракция `Marker` на любой `MarkerHost`
(соло-карта, стопка карт, стопка фигур — метка не знает про `Card`). `MarkerHost` = `slotPos()` +
`state()` (`{atHome,total}`) + опц. `makePayload(cp)` (как схватить цель — только у драггера).
Видимость — декларативный предикат `ShowWhen` по состоянию: `showAlways`/`showAway`/`showEmpty`/
`showGone`. Драггер↔якорь свапаются автоматически: драггер виден пока `atHome>0`, якорь — по своей
политике. Драггер интерактивен + `follow` (едет за пальцем поверх пачки); якорь — просто метка дома.

В песочнице три стопки демонстрируют разные политики якоря (`когда унесли`/`когда пусто`/`всегда`)
и разные иконки (якорь/кольцо/ромб) при общем драггере. Покрыто: `marker.test.ts` (предикаты) +
e2e (свап драггер→якорь после сожжения стопки). `reapDead` теперь чистит `byId`, чтобы метки видели
`total--`.
